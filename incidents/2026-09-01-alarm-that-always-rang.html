Why fix 1 still rang — the line, dissected

This is the real line from the first pass after fix 1, event-gate-00143-ccj at 15:31:11Z. The sweep is reporting that nothing went wrong. Fix 1 searched it for the substring error:

ERRORbooking sweep: {"ok": true, "dry_run": false, "scanned": 106, "skipped": 52, "deferred": 0, "residue": 0, "errors": 0, "errors_detail": [], "snapshot": "loaded", …}

A line saying “zero errors” set off the error alarm. And drop-sweep’s healthy summary — "media_failures": 0, "receipt_failures": 0 — was queued up to do the same on the substring failure.

The problem

A sweep summary is JSON. A sweep complaint is prose. The same words live in both, and a substring search cannot tell a key from a sentence.

Fix 2 reads it in two passes

1. Read the JSON counters as counters. A trouble-named key rings only when it holds a non-zero number or a non-empty list.
2. Strip the pairs out and read what is left as prose.

INFObooking sweep: {"ok": true, … "errors": 0, "errors_detail": [], "snapshot": "loaded", …} ← counters: all zero / empty. prose remainder: "booking sweep:" — nothing to ring on.
ERRORalarm watch panel read failed (1): TimeoutError: The read operation timed out ← no counters. prose says failed. rings.

A counter saying zero is the strongest possible statement that nothing went wrong. It must never be what sets off the alarm.

What to keep

Judge a log line by what it says, not by which callback it came through. A progress callback is a pipe, not a severity.

A count of zero is not a keyword. Anything that reads log text for trouble words has to read counters first, or it will ring on the healthiest line the service can produce.

deploy.sh ships the tree it lives in. Deploy from the checkout that holds the commit you mean, then read git_sha and code_fingerprint back from /health before believing it. A matching fingerprint is the only cheap proof of which code is live; a mismatched one is the only cheap tell.
