The pipes — what happens without you

Five flows, left to right. Click any hop for its full detail (panel at the foot). Green hops keep running in a token outage; amber hops stop; violet is you.

1 · A renter texts SMS · survives outage until the reply step
Phone.com SMS→ event-gate 1-min poll→ emergency?🚨 on-call SMS+Staff Call Queue simple question?quick-answer card everything elseResponder 30-min→held draft · you release→send engine

Without you: emergencies summon staff and simple questions get answered even in a full token outage. A judgment reply is drafted within ~30 min but nothing sends until a human releases it.

2 · An email arrives business Gmail · the weakest inbound pipe
Business Gmail→ gmail_pull ledger→ Concierge 2-hourly triage→ Notion tickets

Without you: mail is archived deterministically, but nothing acts on it until an LLM pass — up to ~2h daytime, ~10h overnight. No emergency regex watches this pipe (fix-list item 3). The ledger cron rides flaky GitHub Actions.

3 · A message goes out every outbound email/SMS · human-gated by design
agent drafts a queue row→ Pending Review · you release→ send engine 1-min poll · v18 guards→ renter

Without you: nothing customer-facing sends — your release is the valve. The engine refuses malformed rows instead of sending them (single sender identity, Invariant J unthreaded-reply guard); failures flip to Error + alert email, never silent. Scheduled FBS sends (HTA/EOB/AVA) flow once queued.

4 · A booking becomes access Skedda → alarm codes · ⚠ upstream data is broken
Skedda ⚠ cookie→ fbs-monitor 15-min rebuild→ Doorman 04:00 + ~06:00→ PIN digits — staff→ HTA with code

Without you: the board rebuilds and the Doorman preflights access 7 days out, checks arm state overnight, and proposes (never executes) code retirements. PIN digits stay human — the panel masks them. Everything here reads through the broken Skedda cookie (fix-list item 1) until it is reseeded.

5 · Something breaks watchers watching workers · deterministic where it counts
fbs-watch 15-min→ Slack #desk-status Sentinel + Watchman hourly→ miss → SMS desk-loop + invariants→ alarm-watchdog DRY RUN→ watchdog log overnight reports→ your morning surfaces

Without you: a fleet outage reaches Slack deterministically; a missed agent run reaches your phone. The alarm watchdog only logs what it would do (fix-list item 4). Everything else lands on the Night Watch / Fixer pages for your morning.

    The phone book can be pruned now — phonecom-cli learns to delete, and 69 junk contacts goNEW TOOL + CLEANUP

    The phone.com surface could only list and create contacts, so a duplicate was uncorrectable by any agent and the address book could only ever grow. client.contact_delete() and python3 -m phonecom contact-delete <id> close that, dry-run by default like every other write in the CLI.

    Deliberately NOT added to the MCP connector. Creation is recoverable, deletion is not, so the fleet still cannot remove a contact — only an attended CLI run can. That asymmetry is the safety property, not an oversight.

    First run took ext100 from 936 to 867: 50 exact duplicates, 13 bare-first-name or character-corrupted variants, 6 decided by reading the Artist Database. Now zero duplicates, zero numbers carrying two names, zero contacts with no number. Full pre-delete backup of all 936 records with every field in outputs/phonecom-backups/.

    The class a duplicate scan cannot see: the book held Kangbin Zhao against the Artist DB's Kangbin Zhou — one person, two surnames, sharing nothing, so no dedup pass would ever pair them. Only a field-by-field comparison against canon finds it. Junyan's ruling the same day, now in job-2-triage.md: the Artist DB is canon for spelling and digits and is fallible — follow it anyway, report a suspected error, never adjudicate one.

  • 2026-08-13 · 19:23Z

    Every Sales SOP that queues an email now names the threading fields — and so does the SOP-authoring pathDOC + GUARD

    Follow-through on the 02:55Z Invariant J guard. All 15 Sales SOPs were read, not sampled. Three are deprecated pointers with no procedure. Of the twelve live ones, every single one that queues an Email row was missing the requirement — the four fixed on 2026-08-12 (Time Slot New Inquiry, Time Slot Renewal, Skedda Booking Inquiry, Platform Booking Inquiry AI-Ready) and the five swept today: AAP / 1AP, Community Rate, Skedda Last-Minute (AI-Ready), Platform Instant Book, Platform Last-Minute (AI-Ready). Each now states, in its Value rules, that an Email row answering an inbound carries Email Subject prefixed Re: and Source Email in hex-id form, copied at triage.

    Three lane-specific carve-outs were written in rather than papered over, because a rule that is wrong in a lane gets ignored in every lane. Community Rate queues three sequential drafts (T1/T2/T3), so it says explicitly that all three are replies — the "only the opening message is a reply" misreading is the live risk there. Platform Instant Book scopes the rule to its fallback path only: the default is an in-thread Gmail reply with the queue row set to Will Not Send, where threading fields are moot, but the documented fallback (staff add the relay to the Artist Page and release the row) does dispatch for real. Skedda Last-Minute is almost all exempt SMS, so it flags only the T1 Email branch — and notes that on a <24h booking a row flipped to Error costs hours there are none of.

    The recurrence was closed at the authoring path, which is the part that mattered. convert-sop-to-ai-ready §1 told authors to cut "generic boilerplate that lives elsewhere (e.g. channel-by-lead-source is in SOP Mapping)" — the instruction that manufactured this defect, since "elsewhere" only works if the agent is reading elsewhere. That bullet now carries an explicit exception for what a step writes, and a new §4 principle requires every queue-write step to name its own fields, on every queue step rather than the first. Mirrored as a short cross-reference in capture-sop-update. Without this, each new SOP written from the templates would have reproduced the gap indefinitely.

    Two things surfaced were closed the same day with Junyan's go-ahead. Platform — Last Minute Booking Request (legacy) now carries the deprecation banner pointing at the AI-Ready page — the 🗺️ SOP Routing DB was checked first and no row pointed at it, so no re-pointing was needed. And the silent SQL omission was reproduced before recording: the identical query over the SOPs data source returned 14 rows in one run and 16 minutes later — transient staleness, not a filter bug. Now a Known-environment gotcha in the workspace CLAUDE.md: a single query-data-sources result is never proof of coverage; cross-check against a second signal before claiming completeness.

  • 2026-08-13 · 02:55Z

    The send engine now refuses an unthreaded reply instead of quietly sending oneGUARD

    A Message Queue row whose Email Subject starts Re: but whose Source Email is blank used to take the brand-new-email path and succeed — the row read Sent, and the renter got a "Re: …" attached to nothing she wrote, splitting her conversation into two threads. Nothing in the outcome distinguished that from a correct reply. Engine v18 checks the pair in validate_(): reply-shaped plus blank field now flips the row to Error with a row comment and an alert email. Live-proven the same night — test row errored ~45s after release, alert quoted the guard's own text, recipient inbox stayed empty (matrix case M10).

    This is Desk Invariant J, which canon had required in prose since 2026-07-09 — and which still lost 7 reply-shaped rows as new threads between Jul 25 and Aug 4, including three on the Anneka K. Peerspace relay. A sent row cannot be repaired, so the check moved to the boundary. The invariant checker still flags J at Pending Review hours earlier; the two surfaces are deliberately different — catch-early versus refuse-late.

    The instructive part is why the field was blank. Canon mandated it in four places, every one of them in the Responder / RESPONSE-RESOLVER / studio-ticket-triage lanes. The row that surfaced this (a time-slot enquiry, caught pre-send) was drafted by the Concierge straight from a Notion SOP whose queue-write step said only "Channel per lead source, held at Pending Review". The rule was written down nowhere the agent was reading at write time. Fixed in three places: that SOP names the field, concierge-orchestration.md binds it to every queue-writing path including SOP steps, and the engine no longer trusts any of them.

  • 2026-08-13 · 02:20–02:30Z

    alarm-watchdog goes live in dry runNEW ROUTE

    Two Cloud Scheduler jobs now tick the new /watchdog route on alarm-mcp: every minute for alarms, every fifteen for bypasses. Deterministic — no tokens, so it keeps watching through an outage.

    It decides and logs; it cannot act. WATCHDOG_ARMED is unset, and the executor that would carry an action out does not exist yet — the route returns 501 even if the variable is set. Two locks, deliberately.

    Purpose once armed: let a tripped siren run 90 seconds, disarm that partition only, re-arm to the mode it was found in. Ceiling of two trips per partition per hour, then it stops and calls a human instead — repeated trips are exactly when a robot should stop silencing an alarm.

  • 2026-08-13 · 02:09Z

    One shared Alarm.com session replaces login-per-callRESILIENCE

    Every panel read used to perform a full login and close it: 14.8 seconds, measured. At one-minute cadence that is ~1,440 logins a day against a provider that locks accounts for repeated authentication — and the token died twice on 2026-08-12 while several surfaces were logging in independently.

    Now: one session, reused. Warm calls run 0.83s. Re-login happens only on session death or after six hours, and exactly once — never in a loop, because a lockout costs the whole system while a missed tick costs sixty seconds. Non-session errors never trigger a retry, so a write that failed mid-flight is never blindly re-run.

    Everything downstream of alarm-mcp gets faster for free, including the presence gate's /panel-states call.
